# Data Pipeline

## Dataset

**DataCo Smart Supply Chain Dataset** (Kaggle), ~180K order-item rows with
shipping, product, customer, and financial attributes.

### Getting the real dataset

1. Download `DataCoSupplyChainDataset.csv` from Kaggle (search "DataCo Smart
   Supply Chain Dataset").
2. Place it at `data/raw/DataCoSupplyChainDataset.csv`.
3. Run `python scripts/run_pipeline.py`.

The raw file is **not** committed to the repository (it's excluded via
`.gitignore`) — both because of size and because redistributing someone
else's dataset isn't appropriate. `data/raw/` and `data/processed/` are
gitignored; `data/external/supplier_master.csv` (synthetic, generated by
this repo) is the exception and is safe to commit.

### Development sample

`scripts/generate_sample_data.py` generates a **deterministic synthetic**
dataset (fixed seed=42) with the exact same raw column schema as the real
Kaggle CSV, so every downstream script works identically against either
source:

```bash
python scripts/generate_sample_data.py --rows 8000 --out data/sample/sample_shipments.csv
python scripts/run_pipeline.py --sample
```

This is what the checked-in demo database was actually built from — **it is
not the real DataCo dataset**, and every place in the UI that surfaces
supplier-level data says so explicitly (`SYNTHETIC DEMO DATA` badges). The
sample generator deliberately encodes realistic delay-rate patterns (Same Day
shipping is riskiest, certain region/category combinations skew worse) so
the ML model has genuine signal to learn from and the analytics pages show
non-trivial results — but the exact numbers are synthetic, not real DataCo
statistics.

## Pipeline stages

```
scripts/ingest_data.py          raw CSV → renamed/typed parquet
scripts/validate_data.py        schema/quality checks, hard-fail vs soft-warn
scripts/clean_data.py           normalize strings, derive shipment_code
scripts/check_data_leakage.py   audit — see below
scripts/feature_engineering.py  causal delay-rate features + synthetic supplier master
scripts/load_database.py        batched (5000/tx) idempotent upsert into MySQL
scripts/compute_supplier_scores.py  supplier scoring + alert rule evaluation
scripts/run_pipeline.py         orchestrates all of the above
```

Every stage prints its own metrics (`records_read`, `records_rejected`,
`records_inserted`, timing) — see the pipeline's stdout, or
`data/processed/data_quality_report.md` for the full quality report.

**Idempotency**: every load target has a unique constraint on a natural key
(`shipment_code`, `source_customer_id`, `supplier_code`, etc.), and
`load_database.py` uses `INSERT ... ON DUPLICATE KEY UPDATE` (or `INSERT
IGNORE` for immutable dimensions) in batches of 5,000 — never one ORM object
per row. Running the full pipeline twice does not duplicate rows; verified
directly (row counts identical after a second run).

## Data quality checks

`scripts/validate_data.py` performs, and reports on:

- Required-field null checks
- Duplicate detection (`(order_id, order_item_id)` business key)
- Invalid dates (shipping before ordering, implausible date ranges)
- Impossible numeric values (non-positive quantity, negative price, discount
  outside [0,1])
- Outlier detection (IQR-based, on sales and scheduled shipping days)
- Class balance of the target (`late_delivery_risk`)

Hard failures are dropped from the pipeline and counted; soft warnings
(unknown categorical values, outliers) are kept and flagged, since the real
Kaggle dataset may contain category spellings this project hasn't
enumerated — dropping on that basis would be too aggressive.

## Target leakage audit — the important part

See [ml-system.md](ml-system.md) and [model-card.md](model-card.md) for the
full write-up. In short: `scripts/check_data_leakage.py` classifies every
column into TARGET / EXCLUDED_LEAKAGE / IDENTIFIER / SAFE_FEATURE /
ADMINISTRATIVE, and **fails the pipeline** if any column is unclassified
(schema drift) or if a feature meant to be safe correlates suspiciously
strongly with the target. It also empirically measures how strongly the
excluded fields (`days_for_shipping_real`, `delivery_status`, `order_status`,
`shipping_date`, `benefit_per_order`) correlate with the target, as evidence
for exclusion rather than an unverified assertion. The generated report is
`data/processed/leakage_report.md`.

## Supplier enrichment layer

The DataCo dataset has no real supplier identity. `ml/features/supplier_master.py`
generates a **deterministic, seeded** pool of synthetic suppliers (4 per
product category), each with a stable-hash-based assignment of shipments to
suppliers (so re-running the pipeline always produces the same assignment).
Every `Supplier` row is flagged `is_synthetic=True`, and the UI shows a
"SYNTHETIC DEMO DATA" badge anywhere supplier-level fields are displayed.
This is clearly documented rather than presented as real company data — see
section 4 of the original spec and [decisions.md](decisions.md).
