# Database Design

MySQL 8, accessed via SQLAlchemy 2.0 ORM + Alembic migrations. See
[decisions.md](decisions.md) for why MySQL over Postgres.

## Schema

| Table | Purpose | Key indexes |
|---|---|---|
| `users`, `roles`, `user_roles` | Auth + RBAC | `users.email` (unique) |
| `customers`, `products`, `orders` | Source-data dimensions from DataCo | unique on `source_*_id` |
| `suppliers` | **Synthetic** demo enrichment layer | `supplier_code` (unique), `supplier_region`, `product_category` |
| `supplier_metrics` | Derived, time-bucketed supplier scores | `(supplier_id, period_start)` composite, `score` |
| `shipments` | Grain = one DataCo order-item; the core fact table | `shipment_code` (unique), `order_date`, `shipping_mode`, `destination_region`, `supplier_id`, `risk_score`, `risk_level`, `status`, `late_delivery_risk`; composite `(order_date, shipping_mode)` and `(supplier_id, risk_level)` |
| `model_versions` | ML model registry | `version` (unique), `status` |
| `shipment_predictions` | One row per (shipment, model_version) inference | composite `(shipment_id, model_version_id)` |
| `shipment_risk_factors` | SHAP explanation rows per prediction | composite `(prediction_id, rank)` |
| `root_causes` | Persisted deterministic root-cause output | `(entity_type, entity_id)` |
| `recommendations` | AI-generated, model-grounded recommendations | `shipment_id` |
| `alerts` | Rule-based operational alerts | `(severity, status)`, `created_at` |
| `ai_conversations`, `ai_messages` | Copilot chat history | `conversation_id` |
| `audit_logs` | Login/logout, alert actions | `(entity_type, entity_id)`, `action` |

Full column-level definitions live in the SQLAlchemy models under
`backend/app/models/` — that is the source of truth; this document describes
intent and indexing rationale, not every column.

## Indexing rationale

Indexes were added for query patterns actually exercised by the API, not
speculatively:

- `shipments.risk_score` / `risk_level` — the shipment explorer and dashboard
  filter/sort on these constantly; both are denormalized onto `shipments`
  from `shipment_predictions` specifically so filtering doesn't require a
  join on the hot path.
- `shipments.(order_date, shipping_mode)` composite — the dashboard's delay
  trend and shipping-mode breakdown both filter by date range and group by
  mode in the same query.
- `shipments.(supplier_id, risk_level)` composite — supplier-scoped risk
  queries (e.g. "this supplier's high-risk shipments").
- `supplier_metrics.(supplier_id, period_start)` — trend queries fetch a
  supplier's metric history in period order.
- `alerts.(severity, status)` — the alert center's default filter combination.

No index exists on low-cardinality columns queried only in combination with
an already-indexed column (e.g. no standalone index on `shipments.status`
beyond what's needed for its own filter).

## MySQL-specific considerations

- **No `NULLS LAST`**: MySQL has no native syntax for it (unlike Postgres).
  Queries that need null-last ordering (e.g. supplier list sorted by score,
  where a brand-new supplier might not have a metric row yet) use an
  explicit `ORDER BY col IS NULL, col DESC` pattern instead of SQLAlchemy's
  `.nullslast()`, which silently emits invalid SQL on the MySQL dialect.
- **Decimal vs. float**: MySQL returns `SUM()`/aggregate results as
  `decimal.Decimal` via PyMySQL, not `float`. Python raises `TypeError` when
  you mix a `Decimal` with a `float` in arithmetic (e.g. `0.0 += Decimal(...)`
  or `Decimal(...) - some_float`). Every aggregation helper in
  `app/repositories/analytics_repository.py`, `app/analytics/root_cause.py`,
  and `app/analytics/supplier_scoring.py` explicitly casts aggregate results
  to `float` immediately after fetching, before any arithmetic.
- **Foreign-key-backed index drops**: Alembic's autogenerated `downgrade()`
  tries to `DROP INDEX` on a composite index before dropping the table that
  owns it; if that index is also the one backing a foreign key, MySQL refuses
  ("needed in a foreign key constraint"). The initial migration's
  `downgrade()` was hand-simplified to just `DROP TABLE` in dependency order
  (children before parents) instead of dropping indexes individually — this
  is safe because dropping a table drops its indexes and FKs together.

## Migrations

```bash
cd backend
alembic upgrade head        # apply
alembic downgrade base      # roll back to empty (tested — see above)
alembic revision --autogenerate -m "description"   # new migration
```

Migrations were verified from a genuinely empty MySQL database (full
`downgrade base` → `upgrade head` cycle), not just "ran once and assumed it
works."
